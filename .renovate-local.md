# Renovate merge guidance

Read by the local Renovate merge skill. The public renovate-eval action and
skill do not read this file.

## What changes what runs

Merging to `main` deploys two kinds of change on its own:

- `kubernetes/`: the ArgoCD Production Deployment workflow syncs every Argo CD
  Application whose path the merge changed (`scripts/argocd-detect-apps`).
- `ansible/`: the Ansible Production Deployment workflow runs the playbook
  through Semaphore on the hosts the merge affects
  (`scripts/ansible-detect-changes`). See `.agents/rules/ansible/semaphore.md`.

A PR whose every changed file is under `kubernetes/` or `ansible/` is deployed
by its merge and checked after it, as below. A PR whose every changed file is
under `opentofu/` deploys nothing, because nothing applies OpenTofu on merge,
but it is validated before merging, as below. A PR whose every changed file is
under `.github/workflows/` or is `.pre-commit-config.yaml` only needs CI. A
workflow update that changes a deploy workflow is exercised by the next merge
that deploys, whose checks would catch a broken deploy.

Nothing else is covered. A PR that changes any other file, such as
`Dockerfile.ansible`, `tests/` or `scripts/`, or that mixes `opentofu/`,
`.github/workflows/` or `.pre-commit-config.yaml` with other files, is merged by
hand.

Kubernetes upgrades are never part of a run. A PR that changes
`kubernetes_short_version` or `kubernetes_version` in
`ansible/group_vars/kubernetes.yaml` upgrades the cluster, patch or minor, and
is merged by hand as `docs/kubernetes-upgrade-playbook.md` describes.

## Before showing the table

For a `kubernetes/` PR, find each changed app's Argo CD Application by its
source path:

```bash
kubectl get applications -A -o jsonpath='{range .items[*]}{.metadata.name} {.spec.source.path} {.status.sync.status}/{.status.health.status}{"\n"}{end}'
```

Record each one's sync and health as they are now, so a problem that was already
there is not blamed on the update. `OutOfSync` with `Healthy` is not a blocker.
A changed path with no Application, one that is `Degraded`, or no cluster access
makes the PR Blocked.

An app's own resources are the ones its Application lists, with their
namespaces; several apps can share a namespace:

```bash
kubectl get application -n argocd APP -o jsonpath='{range .status.resources[*]}{.kind} {.namespace}/{.name}{"\n"}{end}'
```

Just before merging, record the status of each of the app's Ingress hosts:
`curl -sS -o /dev/null -w '%{http_code}\n' --max-time 15 https://HOST/`, with
the hosts from
`kubectl get ingress -n NAMESPACE NAME -o jsonpath='{range .spec.rules[*]}{.host}{"\n"}{end}'`.

For an `ansible/` PR, the Ansible Production Deployment workflow must be enabled
(`gh workflow list -R claytono/infra --all`). Checking the service afterwards
may need SSH to its hosts; when it does, option 1's plan names that SSH, so
choosing it authorizes it.

## Validating OpenTofu, before merging

In a worktree at the PR's head, read `opentofu/README.md` and the README of
every OpenTofu root the PR changes, and validate the way they say. Never run
`tofu init -upgrade` or `tofu apply`. 1Password may prompt for each plan, so
save every command's output to a file in the run directory. If OpenTofu cannot
see resources that already exist, a plan that shows them as new is not a real
change; use the validation that root's README gives instead.

A passing validation covers the PR's fingerprint, not only the commit checked
out: if Renovate rebases the PR after another merge and the fingerprint is
unchanged, do not validate it again. If tracked files in the worktree changed,
stop and report them; never discard them.

## Checking it, after merging

Wait for the deployment workflow's push run for the merge commit, then check
what it deployed. A normal rollout, pods being replaced and temporary
progressing states are expected.

`kubernetes/`: each changed app's Application must be `Synced` and `Healthy` at
a revision that contains the merge commit. Then check the app itself:

- its rollouts finished, its pods are ready and run the expected image, and no
  pod restarted or logged a warning event since the rollout;
- every Ingress host recorded before the merge gives the same status again. A
  5xx, a timeout or a working status turning into an error is a problem; a
  status that was already an error before the merge is reported, not blamed;
- its logs in Loki show no new errors. For each of its workloads, compare the
  error lines from the 15 minutes before the merge with those since the rollout,
  for example
  `logcli query --from=START --to=END --limit=200 '{namespace="NAMESPACE", pod=~"WORKLOAD-.*"} |~ "(?i)error|fatal|panic|exception"'`.
  An error message that appears only after the rollout, or one that repeats much
  more often, is a problem. If a query returns as many lines as its limit, raise
  the limit and run it again, so neither period is cut off.

`ansible/`: watch the Ansible Production Deployment run through to Semaphore
finishing. Trust the workflow's choice of hosts: a play on all hosts, activity
on other hosts or an empty Semaphore limit is not a problem. Find the hosts that
run the service the PR changed, and check over SSH on each that its systemd unit
or container is running on the new version, restarted by this deploy, and that
its logs since the restart (`journalctl -u UNIT --since TIME` or
`docker logs --since TIME CONTAINER`) show no errors or repeated restarts. Host
logs are not in Loki, so only the time since the restart can be checked.

## Checking the app came back up

The checks above apply to every app. Then, for each changed app or service, work
out from its `kubernetes/<app>/` files or Ansible role what it does here: what
it serves, what it connects to, and what work it does on its own. Check that it
is doing that again:

- Read its logs since the restart through its startup: it loaded its
  configuration, connected to its database and other dependencies, and reached
  its normal running state, with no errors along the way.
- Make test requests the way its users do: for a web app or API, a page or
  endpoint beyond `/` that needs its backend, such as a status, health or list
  endpoint; for something other apps use, a request from their side.
- For work it does continuously, such as a sync loop or an exporter, confirm it
  is doing it again, in its logs or its output; for an exporter, that its
  metrics are being scraped. Do not wait for a scheduled job's next run.

Work these checks out during the run, never before the table: plan the first
PR's while its gate waits, and each later PR's while the PR before it waits for
its `main` runs and deploy. Say what you planned in one line when you plan it.
Record the baseline the checks compare against just before that PR's merge. When
the run includes `ansible/` PRs, option 1 says "including SSH health checks for
the affected Ansible hosts", so choosing it allows that SSH. Every check is
read-only: requests only read, and never restart, change configuration or write
data to check something. A check that fails is a problem with the deployed
update.
